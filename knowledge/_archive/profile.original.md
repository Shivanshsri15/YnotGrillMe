### Offline-first mobile architecture: detailed explanation

The mobile application needed to remain useful to field users when network connectivity was unavailable or unreliable. Users needed to read previously fetched data, make local changes, retain pending operations, retry failed requests, avoid duplicate operations, handle conflicts, and resume synchronization when connectivity returned.

The technical lead constrained unnecessary architectural complexity and prohibited introducing another database such as WatermelonDB. The implementation therefore used local key-value storage, endpoint-addressable cached responses, and a pending-operation queue.

The documented data flow is:
1. Fetch data from an API.
2. Store the response locally, using the endpoint as the key and the response as the value.
3. Serve locally stored data when a screen is used offline.
4. Update local data and UI state when the user makes a change.
5. Store the pending endpoint-and-payload operation in a queue.
6. Process queued operations when connectivity permits.
7. Acknowledge and remove successful operations.
8. Retain failed operations for appropriate retries.

The transcript emphasizes that local caching and mutation synchronization are separate concerns. A cached response enables offline reads; the operation queue represents changes that still need to reach the server.

The queue processed operations in FIFO order and the mock discussion described an approximately two-second gap between operations. This favors predictable ordering and simpler debugging but may reduce throughput. Potential future improvements—such as bounded concurrency for independent operations, batching, exponential backoff with jitter, and queue-age/retry monitoring—were discussed as possible improvements, not as claims about the original implementation.

The implementation included connectivity handling, retries, change tracking, conflict resolution, and background batching. Do not claim a particular retry schedule or delivery guarantee beyond what is documented.

#### Idempotency and retry semantics

A client can send a request, lose the connection before receiving the response, and be unable to know whether the server completed the operation. Retrying may therefore execute the same logical operation twice unless the server supports idempotency.

The transcript identifies the key requirements for a robust approach:
- Generate an operation identifier when the logical operation is first created.
- Persist it with the queued operation.
- Reuse the same identifier for every retry of that operation.
- Have the server atomically check and record the identifier.
- Return the prior result for duplicate attempts when appropriate.

A unique request ID alone does not guarantee exactly-once execution. The backend must enforce the deduplication behavior, and the check-and-record operation must be safe against concurrency. Do not claim the original system guaranteed exactly-once execution.

#### Conflict resolution and versioning

The transcript says timestamps were used as part of conflict handling and explicitly acknowledges that versioning would be stronger in some situations. When a device is offline, another user may change the server record before the device reconnects. The local edit can then be based on stale state.

Timestamps can suggest recency but are vulnerable to clock skew, close-together updates, and business rules that cannot be reduced to “latest timestamp wins.” A stronger alternative is optimistic concurrency using a record version or revision:
- Client reads version 12.
- Another user updates the record to version 13.
- Client submits its change with expected version 12.
- Server detects that the record has changed and rejects or flags the stale update.
- Client retrieves the latest record and applies an appropriate reconciliation policy.

This version-based approach was discussed as an improvement, not as an already completed feature. The interview lesson is that offline-first architecture is a distributed state-management problem, not simply caching.
